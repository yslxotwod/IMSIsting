# tools/lte-corpus — real captured LTE RRC/SIB bytes

This directory holds LTE RRC PDUs that were **captured from real hardware on a
real network** — not generated by any encoder, and not produced by pycrate — plus
the assertions that check our codec against them.

## Why this exists

`tools/lte_asn1.py` (+ `tools/lte_rrc_layout.py`, `tools/lte_per.py`) is proven
correct against exactly one independent implementation: the ASN.1 library
pycrate 0.8.1, used as a build-time oracle by `tools/check-lte-sib-codec.sh`.
pycrate implements TS 36.331 from the same document we do, so a clause that both
we and pycrate misread stays invisible: every check still passes and every
vector still "decodes".

`docs/OFFENSIVE_ROADMAP.md` (lines ~774-790) demands that every construction be
asserted against a published vector or an independent implementation, not
against its own output. This corpus closes the remaining half of that gap: the
bytes come from the air, and the expected values come from a third
implementation, Wireshark's C `lte-rrc` dissector, reading the same capture.

## What is here

| file | what |
|---|---|
| `pdus/*.pdu.hex` | the captured PDU bytes (one PDU per file, hex, no framing) |
| `vectors.json` | provenance, licences, upstream URLs + sha256, expected values, negative and mutation controls, coverage gaps |
| `extract.py` | pulls the RRC PDUs out of the two upstream pcaps (GSMTAP and srsRAN mac-lte-framed) |
| `check_corpus.py` | the assertion engine |
| `README.md` | this file |

`./tools/check-lte-corpus.sh` is the entry point. Nothing here writes into the
repository, and the default run needs no network.

## Vectors

Expectations were read out of Wireshark's dissection of the same capture
(`tshark -V`), never out of our own decoder.

| vector | command | bytes | decoded (asserted) |
|---|---|---|---|
| `qcsuper-sfr-band3-cell320515` | `decode` | 26 | mcc 208, mnc 10, plmn_count 2, tac b5ad, cellid 004e403, notBarred, allowed, q_rx_lev_min -65, p_max 23, band 3, ms10, value_tag 23, scheduling rf16 / rf16 sibType3 / rf16 sibType4 / rf32 sibType5 / rf16 sibType6, bits_consumed 194 |
| `qcsuper-sfr-band7-cell320512` | `decode` | 26 | same network, cellid 004e400, band 7, value_tag 22 |
| `ltesniffer-srsenb-band7-cell105217` | `decode` | 18 | mcc 901, mnc 55, plmn_count 1, tac 0007, cellid 0019b01, q_rx_lev_min -65, band 7, ms20, value_tag 0, scheduling rf16 sibType3, bits_consumed 118 |
| `ltesniffer-srsenb-si-sib2-sib3` | `si` | 41 | SystemInformation container: sib_count 2, first sibType2, 14-bit header, 314-bit body, 328 total bits |

On top of the exact values above, every decoded field is checked for
*plausibility* so that a decode which "succeeds" with nonsense still fails:
MCC is 3 digits in the ITU assigned range 200..999, MNC 2-3 digits, PLMN count
1..6, TAC non-zero and not 0x0000/0xFFFE/0xFFFF, cell identity non-zero inside
28 bits, `freqBandIndicator` a defined band (1..64), `q-RxLevMin` inside
-70..-22 as TS 36.331 requires, `p-Max` inside -30..33,
`systemInfoValueTag` 0..31, `si-WindowLength` and every `si-Periodicity` one of
the enumerated values, no SIB scheduled twice, no unknown `sibType`, and
`bits_consumed` consistent with the capture length. For the `si` container the
header/body/total bit counts must add up to exactly 8 x the captured bytes and
the hex-body padding bits must be zero.

Two further controls keep the assertions honest:

* **Negative controls** — a SystemInformation container must be refused by the
  SIB1 entry point, and our SIB2 decoder must keep failing on the real network's
  `soundingRS-UL-ConfigCommon` release form (a codec gap asserted so it cannot
  change silently).
* **Mutation controls** — corrupting one bit of six different bytes must change
  the decoded value (mcc 208->248, mnc 10->90, tac b5ad->35ad,
  cellid 004e403->804e403, band 3->1, value_tag 23->19) and corrupting the
  first byte must make the decode fail outright. This proves the assertions bind
  to the captured bits rather than to a filename.

## Sources, provenance and licences

Both upstream containers are copyleft, and this repository declares no licence
of its own (there is no LICENSE file at the top level). Therefore **no pcap is
vendored here**; we would be re-licensing third-party bytes that we cannot
re-license. What is stored is the small factual PDU extract (raw over-the-air
data) together with its exact provenance, and the checker can re-fetch the
upstream file, verify its sha256 and require the re-extracted bytes to be
byte-identical to the vendored ones. That way the vendored hex is provably
capture data: `./tools/check-lte-corpus.sh <workdir> --upstream`.

## How to run

```sh
./tools/check-lte-corpus.sh                 # offline: vendored bytes only
./tools/check-lte-corpus.sh /tmp/lte-work --upstream   # fetch + re-extract (network)
python3 tools/lte-corpus/check_corpus.py    # the engine directly, no work dir
```

Exit: `0` every assertion holds, `1` an assertion failed, `2` could not set up
(missing corpus, missing codec, missing/unfetchable upstream capture). A failure
is never a skip.

## What this does NOT cover (stated, not papered over)

* **SIB2 and SIB3 are captured but not asserted.** The LTESniffer SI container
  really does carry SIB2 and SIB3 (Wireshark confirms both, with all their
  fields), but our codec cannot decode those bodies: `sib2-decode` fails on the
  real `soundingRS-UL-ConfigCommon` **release** form (we model only setup), and
  `sib3-decode` models only the *absent* forms of `s-NonIntraSearch` /
  `s-IntraSearch` / `p-Max` while the real SIB3 carries them. `SIB4..SIB13` are
  therefore **not** asserted against any real capture at all. Fixing the codec to
  decode these would be the highest-value follow-up.
* **Only one commercial network.** One source (SFR France) is a commercial
  network; the other three vectors are a laboratory testbed. No second operator
  was found under a licence that permits reuse, so "real network" here means
  *one* real network.
* **Wireshark shares our reading of TS 36.331.** Wireshark's lte-rrc dissector
  implements the same unaligned-PER rules as pycrate and our engine, so a
  misreading shared by all three would still be invisible. What this corpus
  eliminates is the different failure mode: bytes that no real network ever
  sends, or a codec that only agrees with pycrate on pycrate-shaped input.
* **Second PLMN not field-checked.** Our `decode` CLI prints only the first
  PLMN, so `plmn_count` 2 is asserted, but the second PLMN of the two SFR
  vectors is only covered by Wireshark's independent dissection, not by our
  codec's output.
* **Weak/partial assertions, explicitly.** `bits_consumed` and the `si` run's
  `body_hex` are our own decoder's output, so they are self-consistency locks
  (bit-length arithmetic and a regression lock), not independent evidence. Every
  other expected value is from Wireshark. Both captures are FDD, Release-8/9
  era: no TDD, no NB-IoT, no Rel-13+ content, no carrier aggregation.
* **Not covered by any vector**: `encode_sib1`, the TDD branch (which this
  decoder refuses by design), and every SIB other than the SIB1 fields listed
  above.

## Sources examined and rejected

* `gitlab.com/wireshark/wireshark` `test/captures/gsmtap_um_lte.pcap` — the only
  LTE-named file among 454 test captures. **Rejected**: link type 0 with
  unresolvable encapsulation, 6 frames on a 1970 epoch with mechanical 6/12/16
  ms spacing — a hand-built dissector test, not a capture. (Also GPL-2.0.)
* **Vienna 4G/5G Drive-Test Dataset** (Zenodo 21372657, CC BY 4.0) — genuinely
  real commercial networks in Vienna (PCTEL IBflex scanner + Nemo Outdoor, 2024-2025),
  but the released tables are harmonised radio KPIs; the documented schema has no
  raw MIB/SIB bytes and no MCC/MNC/TAC columns. **Rejected** as a byte source.
* `falkenber9/falcon-examples` (**MIT**) — a real O2-DE (MCC 262 / MNC 03)
  over-the-air IQ recording from 2019-04-15, shipped with a cell list giving
  TAC 35160, cell identity 13884163, PCI 50, EARFCN 6200 (band 20). This is the
  best remaining commercial-network lead, but turning IQ into SIB bytes needs
  the full AGPL-3.0 FALCON PHY receiver (PSS/SSS/PBCH/PDCCH/PDSCH). **Recorded
  as a lead, not used.**
* MobileInsight `examples/logs/*.mi2log` — real US commercial handset logs
  (strings show MCC 311 / MNC 480, Verizon), but the container is a proprietary
  `BinaryStruct` format and the repository licence is `NOASSERTION` (unclear).
  **Provenance recorded, nothing copied.**
* Zenodo 8013704 "Instructions Unclear: Undefined Behaviour in Cellular Network
  Specifications" (AGPL-3.0-or-later) — modified srsRAN plus TLA+ models and
  generated test cases; no real captures. **Rejected.**
* `srsran/srsRAN_4G` (AGPL-3.0) — its test vectors are PHY-layer `.dat`/`.bin`
  (signal files, NB-IoT/SIB PHY captures), no RRC pcaps. `kit-cel/gr-lte`
  (GPL-3.0) ships no pcaps. 3GPP/ETSI TS 36.331 itself contains no byte-level
  test vectors, and the Wireshark wiki sample-capture page lists no LTE capture.
